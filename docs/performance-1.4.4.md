# 1.4.4 内存与流畅度优化记录

2026-09-20，优化版源码，尚未发布 GitHub Release。

## 为什么一个状态提示工具可能占用一百多兆

这里的程序是输入状态提示工具，内存不只用于绘制两个字，还包括 .NET / WinForms、绘图资源、跨进程辅助功能接口和运行时缓存。任务管理器中的内存读数与托管对象大小不是同一个指标。

本次检查确认旧代码存在可减少的开销：每 100 ms 生成完整诊断文本和显示状态字符串；跟随气泡每次移动都创建 DIB、复制像素并重新上传；旧版文本定位使用托管 UIA 包装对象，资源回收依赖终结器；Java 后台线程在未使用 Java 时也已创建。

没有取得用户运行数天后的进程快照，因此不能断言一百多兆全部由泄漏造成，也不能保证每种应用组合都固定低于某个数值。本次没有使用强制 GC、工作集裁剪或定时重启来降低显示数字。

## 修改

- 诊断按需生成，状态比较直接比较字段。
- 气泡移动复用已经提交的透明画面，减少重复绘图上传；内容、尺寸、方向、颜色、透明度变化仍正常刷新。
- 旧版 TextPattern 与 TextPattern2 统一使用原生 UIA；查询完成后释放接口、范围和范围数组，并复用已取得的控件标识。旧版接口的空选区规则依据 [Microsoft GetSelection 文档](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomationtextpattern-getselection)。
- Java 工作线程按需启动；Windows 光标查询空闲 30 秒后释放 UIA 连接，线程保持可复用。启用跟随后仍维持约 100 ms 轮询，隐藏倒计时气泡时仍能检测输入框切换。
- “复制状态诊断”加入工作集、私有内存、托管堆大小、GDI / USER 资源数和运行时长，不读取输入文本。

## 同机短时对比

两份源码分别编译为优化开启的 AnyCPU 测试程序，使用相同窗口、相同负载、独立进程顺序运行。预热之后测量，不调用强制垃圾回收。累计分配使用 AppDomain 计数，含测试进程其他托管活动；它不是常驻内存或节省的物理内存。

| 场景 | 1.4.3 累计分配 | 1.4.4 累计分配 | 分配减少 | 单次测量耗时变化 |
| --- | ---: | ---: | ---: | ---: |
| 20,000 次状态轮询 | 50,997,456 B | 1,089,536 B | 97.9% | 153 → 96 ms |
| 2,000 次气泡移动 | 6,069,192 B | 2,816,480 B | 53.6% | 2,255 → 1,034 ms |
| 2,000 次静止气泡更新 | 4,157,616 B | 1,622,016 B | 61.0% | 138 → 39 ms |

耗时受桌面合成、系统负载影响；以上不是延迟保证。测试窗口与被测工具处于同一进程，不能代表全部第三方跨进程提供者。

新版另进行了 5,500 次现代 UIA 和 5,500 次旧版 UIA 查询（均含预热），全部取得有效光标。旧版接口五个测量批次结束时的私有内存约为 32.09、32.29、32.34、32.49、32.57 MiB；最终工作集约 52.4 MiB。所有测量批次 GDI 数量无增长、USER 数量无增长或下降。该结果说明本地短测没有出现 GUI 资源累积，不能替代连续数天的观察。

182 项功能自动检查通过，包括真实 RichEdit 光标、旧版 UIA 选区回退、排除非空选区、连接重建、隐藏恢复、透明度、不抢焦点、输入框切换时长及防误触发。此次未重新执行真实 Java / IDEA 集成测试，也未覆盖所有浏览器、微信和多屏 DPI 组合。

## 使用与复测

先退出旧版，再运行 `local-preview-v1.4.4/键盘状态.exe`，已有设置保留。新版尚未修改 GitHub 发布文件。

若实际使用数天后占用仍持续上升，可分别在刚启动、工作数小时、出现高占用时使用“复制状态诊断”，比较相同显示设置下的私有内存、托管堆和 GDI / USER 数量。

```powershell
.\build.ps1 -Test -OutputDirectory .\local-preview-v1.4.4
.\tests\test-performance.ps1
```

性能测试使用自己的窗口和数据，不修改用户设置。它采用正常 WinForms 消息循环，避免轮询等待人为放大 UIA 调用耗时。
